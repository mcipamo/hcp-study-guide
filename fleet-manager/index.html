    Fleet Manager Operations¶

    OSD Fleet Manager (OSDFM) manages the infrastructure of Service Clusters (SC) and Management Clusters (MC). This page covers the OSDFM API, common operational tasks, and the MC/SC lifecycle.

    Listing and Finding SC/MCs¶

    # List all Service Clusters
ocm get /api/osd_fleet_mgmt/v1/service_clusters | \
  jq -r '.items[] | [.id, .status, .region.id, .cloud_provider.id] | @tsv'

# List all Management Clusters
ocm get /api/osd_fleet_mgmt/v1/management_clusters | \
  jq -r '.items[] | [.id, .status, .region.id] | @tsv'

# Find which MC serves a specific HCP cluster
ocm get /api/osd_fleet_mgmt/v1/management_clusters | \
  jq -r '.items[] | select(.managed_clusters[]? | .cluster_management_reference.cluster_id == "<HCP_CLUSTER_ID>") | .id'

# Find a cluster's MC using backplane
ocm backplane login $HCP_CLUSTER_ID --manager
# The management cluster context will be active

# Get the MC's cluster ID from the internal cluster ID
ocm get /api/osd_fleet_mgmt/v1/management_clusters | \
  jq -r '.items[] | select(.cluster_management_reference.cluster_id == "<MC_INTERNAL_ID>") | .id'

    Maintenance Mode¶

    Maintenance mode prevents new HCPs from being scheduled to an MC or SC while keeping existing HCPs running.

    When to Use Maintenance Mode¶

    • Before upgrading an MC or SC
    • When investigating a node-level issue on an MC
    • When an MC shows elevated error rates but HCPs are still functioning

    Enabling Maintenance Mode¶

    # Put an MC into maintenance mode (no new HCPs assigned)
ocm patch /api/osd_fleet_mgmt/v1/management_clusters/$MC_ID \
  --body='{"status":"maintenance"}'

# Put an SC into maintenance mode
ocm patch /api/osd_fleet_mgmt/v1/service_clusters/$SC_ID \
  --body='{"status":"maintenance"}'

    Exiting Maintenance Mode¶

    # Bring an MC back to active
ocm patch /api/osd_fleet_mgmt/v1/management_clusters/$MC_ID \
  --body='{"status":"ready"}'

    Maintenance mode does not affect existing HCPs

    Customers on the MC continue to have their clusters running. Only new cluster creation is blocked.

    Creating a New Management Cluster¶

    New MCs are created via a two-step process:

    Step 1: Request via OSDFM API¶

    ocm post /api/osd_fleet_mgmt/v1/management_clusters \
  --body='{
    "region": {"id": "us-east-1"},
    "cloud_provider": {"id": "aws"},
    "management_cluster_parent": {
      "service_cluster": {"id": "'$SC_ID'"}
    }
  }'

    This creates the MC record and triggers OSDFM to provision a new cluster.

    Step 2: Configure via app-interface¶

    New MC configuration (machine pools, autoscaling, labeling) is done via app-interface MRs targeting the OSDFM configuration.

    Deleting a Management Cluster¶

    Deleting an MC requires migrating all HCPs first (no live migration exists — this requires customer coordination for each HCP).

    Two-Step Delete¶

    # Step 1: Drain (move MC to 'draining' state — no new HCPs, existing can be migrated)
ocm patch /api/osd_fleet_mgmt/v1/management_clusters/$MC_ID \
  --body='{"status":"draining"}'

# Step 2: Delete (only after ALL HCPs migrated/deleted)
ocm delete /api/osd_fleet_mgmt/v1/management_clusters/$MC_ID

    Pre-delete verification

    # Confirm no HCPs remain on this MC
ocm get /api/osd_fleet_mgmt/v1/management_clusters/$MC_ID | \
  jq '.managed_clusters | length'
# Must be 0 before deletion

    Region Operations¶

    Disable a Region¶

    Disabling a region prevents new clusters from being created in it. Existing clusters are unaffected.

    # Disable region creation
ocm patch /api/osd_fleet_mgmt/v1/regions/us-east-2 \
  --body='{"cloud_provider":{"id":"aws"},"enabled":false}'

    Cycle a Region (replacement rollout)¶

    Cycling replaces SCs and MCs in a region with new infrastructure. This is used after major OS upgrades or when fundamental infrastructure needs replacement.

    # 1. Create new SC in the region
ocm post /api/osd_fleet_mgmt/v1/service_clusters \
  --body='{"region":{"id":"us-east-2"},"cloud_provider":{"id":"aws"}}'

# 2. Wait for new SC to be ready
ocm get /api/osd_fleet_mgmt/v1/service_clusters/$NEW_SC_ID | jq -r '.status'

# 3. Disable old SC (maintenance mode)
ocm patch /api/osd_fleet_mgmt/v1/service_clusters/$OLD_SC_ID \
  --body='{"status":"maintenance"}'

# 4. Create new MCs on the new SC
# (follow Create New MC procedure above)

# 5. Migrate HCPs from old MCs to new MCs (customer coordination required)

# 6. Delete old MCs (after all HCPs migrated)
# 7. Delete old SC (after all MCs deleted)

    Full Region Rollout (8-step process)¶

    When rolling out a new OCP version to all clusters in a region:

    1. Set version block on main fleet (prevent uncontrolled upgrades)
    2. Upgrade canary sector SC + MCs (verify stability)
    3. Remove version block from sector 1
    4. Upgrade sector 1 SC + MCs (verify)
    5. Progress through sectors 2, 3, 4 in sequence
    6. Update fleet-wide version to allow customer clusters to auto-upgrade
    7. Monitor for 24 hours post-upgrade
    8. Remove version blocks

    Override Hypershift Image¶

    In emergency situations (hotfix before a new release), the HyperShift Operator image can be overridden on an MC:

    # Override the HyperShift image on a specific MC
ocm patch /api/osd_fleet_mgmt/v1/management_clusters/$MC_ID \
  --body='{
    "hypershift_config": {
      "operator_image": "quay.io/hypershift/hypershift-operator@sha256:<new-sha>"
    }
  }'

    Temporary measure only

    Image overrides are reverted on the next OSDFM reconciliation cycle unless made permanent via app-interface.

    Fleet Upgrades¶

    Upgrade Mechanism (AUS + MUO)¶

    Fleet upgrades use three interconnected services:

    Service Role
    AUS (Advanced Upgrade Service) Schedules and gates upgrades per sector
    CVO (Cluster Version Operator) Applies the upgrade on each cluster
    MUO (Managed Upgrade Operator) Orchestrates worker/control-plane upgrade timing

    Version Blocks¶

    Version blocks are regex patterns applied per sector to prevent premature upgrades:

    # Example: Block all 4.17.x until validated
# Applied via app-interface to AUS configuration
version_block: "^4\\.17\\..*"

# Block a specific z-stream with a known bug
version_block: "^4\\.17\\.2$"

    Version inheritance prevents production from upgrading past what's been validated in stage.

    Updating a Management Cluster Offline¶

    When a MC's API is unresponsive but the cluster's AWS resources are intact:

    # Connect via break-glass kubeadmin credentials
# (stored in OSDFM secrets or Vault)
oc get secret -n kube-system kubeadmin -o jsonpath='{.data.password}' | base64 -d

# OR connect via instance (SSM + node access)
aws ssm start-session --target $INSTANCE_ID

    Short-Lived Test Clusters¶

    OSDFM supports creating short-lived test SCs and MCs (used by CI pipelines):

    # Create a short-lived SC (expires automatically after TTL)
ocm post /api/osd_fleet_mgmt/v1/service_clusters \
  --body='{
    "region": {"id": "us-east-2"},
    "cloud_provider": {"id": "aws"},
    "expiration_timestamp": "2025-12-01T00:00:00Z"
  }'

    Cleaning Up Leftover AWS Resources¶

    After MC/SC deletion, some AWS resources may remain (EBS volumes, ENIs, load balancers):

    # List orphaned EBS volumes tagged with the MC's cluster ID
aws ec2 describe-volumes \
  --filters "Name=tag:kubernetes.io/cluster/$MC_INFRA_ID,Values=owned" \
  --query 'Volumes[*].[VolumeId,State,Size]'

# List orphaned load balancers
aws elb describe-load-balancers \
  | jq -r '.LoadBalancerDescriptions[] | select(.LoadBalancerName | contains("'$MC_INFRA_ID'"))'

# Snapshot before deleting (if large volumes)
aws ec2 create-snapshot --volume-id $VOL_ID \
  --description "pre-cleanup snapshot $MC_ID $(date +%Y%m%d)"
