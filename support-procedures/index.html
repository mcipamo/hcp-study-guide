    Support Procedures¶

    Operational procedures for common customer-facing support scenarios: limited support, end-of-life handling, escalation, backups, and cluster configuration changes.

    Limited Support¶

    Limited support restricts what engineering teams are obligated to fix, while preserving the customer's ability to use their cluster. It's used when the customer has violated a support condition (e.g., non-standard configuration, unpaid subscription).

    Limited Support Lifecycle¶

    sequenceDiagram
    participant SRE
    participant osdctl
    participant OCM
    participant Alerts

    SRE->>osdctl: cluster support post
    osdctl->>OCM: POST /api/accounts_mgmt/v1/support_exceptions
    OCM-->>osdctl: OK (limited support active)
    Note right of OCM: Alert suppression label<br>added to HostedCluster
    OCM-->>Alerts: Silence all [HCP] alerts for cluster
    Note over SRE,Alerts: Customer can still use cluster<br>but SRE is not alerted

    SRE->>osdctl: cluster support delete
    osdctl->>OCM: DELETE support exception
    OCM-->>Alerts: Restore alert routing

    osdctl Commands¶

    # Post limited support
osdctl cluster support post $CLUSTER_ID \
  --reason "L<reason-code>" \
  --note "Customer has modified managed resources in violation of support policy. OHSS-XXXX"

# Check current limited support status
osdctl cluster support status $CLUSTER_ID

# Delete limited support (restore full support)
osdctl cluster support delete $CLUSTER_ID

    Use status not list

    The correct subcommand is status, not list. osdctl cluster support list does not exist.

    Alert Suppression (Manual)¶

    For temporary alert suppression without full limited support status:

    # Add suppression label to HostedCluster
ocm backplane login $CLUSTER_ID --service
ocm backplane elevate "$JIRA_TICKET" -- \
  -n $MC_NAMESPACE label manifestwork $CLUSTER_ID \
  "hypershift.openshift.io/suppress-alerts=true"

    End-of-Support Handling¶

    When a cluster reaches an unsupported version, SRE must initiate an upgrade.

    Process A: EUS Transition (Even y-streams → Extended Update Support)¶

    For clusters running an even y-stream (e.g., 4.16, 4.18) where an EUS→EUS upgrade path exists:

    # Transition the cluster to its EUS path
osdctl hcp transition-to-eus --cluster-id $CLUSTER_ID

# What this does:
# 1. Verifies the cluster is on an eligible even y-stream
# 2. Configures the upgrade policy for the EUS channel
# 3. Schedules the upgrade via OCM

    Process B: Force Upgrade (Odd y-streams → next y-stream)¶

    For clusters running an odd y-stream (e.g., 4.15, 4.17) that have no EUS path:

    # Force-upgrade to the next supported version
osdctl hcp force-upgrade --cluster-id $CLUSTER_ID --target-version 4.18.x

# What this does:
# 1. Creates an upgrade policy bypassing customer consent
# 2. Logs the action with the OHSS ticket
# 3. Triggers the upgrade immediately

    Which Process?

    Current Version Strategy
    4.12, 4.14, 4.16, 4.18 (even) Process A: transition-to-eus
    4.13, 4.15, 4.17, 4.19 (odd) Process B: force-upgrade

    Pre-EOS Communication¶

    Before forcing an upgrade, always: 1. Confirm the cluster ID and current version 2. Open an OHSS ticket for tracking 3. Check for customer open cases (may be aware and working on it) 4. Send customer notification (templates in Confluence)

    Backup Enable/Disable¶

    OADP/Velero backups can be enabled or disabled per-cluster. Backups are enabled by default for all ROSA HCP clusters.

    # Check current backup configuration
ocm backplane login $CLUSTER_ID --manager
oc get backupstoragelocation -n openshift-adp

# Check backup schedule
oc get schedule -n openshift-adp | grep $CLUSTER_ID

# Disable backups (for a cluster that is being deleted)
# 1. Remove the DR ManifestWork (step 2 only, NEVER step 1)
ocm backplane login $CLUSTER_ID --service
ocm backplane elevate "$JIRA_TICKET" -- \
  delete manifestwork ${CLUSTER_ID}-01-dr -n $MC_NAMESPACE

# Enable backups (re-create from OSDFM template)
# This is done automatically by OSDFM when a cluster is created
# For manual re-enable, contact the OSDFM team

    Never delete -00-dr first

    Always check the order: -01-dr (DR credentials) can be deleted and recreated. If you delete -00-dr (BackupStorageLocation) first, Velero loses its storage config and cannot back up or restore.

    Canary Sector¶

    The canary sector is a set of clusters upgraded first within each region to validate new versions before the full fleet upgrade.

    # Check which clusters are in the canary sector
ocm get /api/osd_fleet_mgmt/v1/management_clusters | \
  jq -r '.items[] | select(.sector == "canary") | [.id, .region.id, .status] | @tsv'

# Promote a non-canary cluster to canary (for testing)
ocm patch /api/osd_fleet_mgmt/v1/management_clusters/$MC_ID \
  --body='{"sector":"canary"}'

# Demote back to standard
ocm patch /api/osd_fleet_mgmt/v1/management_clusters/$MC_ID \
  --body='{"sector":"main"}'

    Replacing the Pull Secret¶

    The global pull secret is used by worker nodes to pull Red Hat images. Replacing it doesn't affect the control plane (which runs on the MC with the MC's pull secret).

    Customer-Initiated (ROSA CLI)¶

    Customers can replace their own pull secret: 

    # Customer command
rosa edit cluster -c $CLUSTER_NAME \
  --pull-secret '{"auths":{"cloud.openshift.com":{"auth":"...","email":"user@example.com"}}}'

    SRE-Initiated (Break-Glass)¶

    If the pull secret is corrupted and the customer cannot rotate it:

    # Get the current pull secret to confirm format
ocm backplane login $CLUSTER_ID
oc get secret pull-secret -n openshift-config \
  -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | jq .

# Create new pull secret (from customer's supplied credentials)
NEW_SECRET='{"auths":{"cloud.openshift.com":{"auth":"<base64-creds>",...}}}'

ocm backplane elevate "$JIRA_TICKET" -- \
  patch secret pull-secret -n openshift-config \
  --type merge \
  -p '{"data":{".dockerconfigjson":"'$(echo $NEW_SECRET | base64 -w0)'"}}'

# Verify MachineConfig propagation (workers will roll with new secret)
oc get mcp

    Shared VPC Clusters¶

    A Shared VPC cluster uses a VPC owned by an organization's "owner" AWS account, with subnets shared to a "consumer" AWS account where the cluster actually runs.

    Architecture¶

    graph LR
    subgraph Owner["VPC Owner Account"]
        VPC["VPC + Subnets\n(shared via RAM)"]
        PZ["Private Hosted Zones\n(Route53)"]
    end
    subgraph Consumer["Cluster Account"]
        CLUSTER["ROSA HCP Cluster\n(control plane + workers)"]
    end

    VPC -->|"RAM share"| CLUSTER
    PZ -->|"VPC association"| CLUSTER
    CLUSTER -->|"creates records in"| PZ

    style VPC fill:#e3f2fd,color:#0d47a1
    style CLUSTER fill:#e8f5e9,color:#1b5e20
    style PZ fill:#ede7f6,color:#4a148c

    Requirements¶

    1. VPC owner must share the subnets to the consumer account via AWS RAM (Resource Access Manager)
    2. VPC owner must grant the consumer's installer role permission to create Route53 records in the private hosted zone
    3. Consumer account creates the cluster using the shared subnet IDs
    4. The installer IAM role in the consumer account must have a cross-account trust policy

    Troubleshooting Shared VPC¶

    # Check if subnet sharing is visible from consumer account
aws ec2 describe-subnets \
  --subnet-ids $SUBNET_ID \
  --query 'Subnets[].{SubnetId:SubnetId,OwnerId:OwnerId,SharedVpc:SharedVpc}'

# Check Route53 PHZ association from consumer account
aws route53 list-vpc-association-authorizations --hosted-zone-id $ZONE_ID

# Check installer role has required cross-account permissions
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::$CONSUMER_ACCOUNT:role/ManagedOpenShift-Installer \
  --action-names route53:ChangeResourceRecordSets \
  --resource-arns "arn:aws:route53:::hostedzone/$ZONE_ID"

    Escalating to Component Engineering Teams¶

    When a case requires engineering investigation beyond SRE scope:

    Internal Escalation Steps¶

    1. Document findings in the OHSS ticket (timeline, evidence, logs already collected)
    2. Open a JIRA bug in the appropriate component project
    3. Link the OHSS to the JIRA for tracking
    4. Post in Slack with @component-team-handle and link both tickets
