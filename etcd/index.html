    etcd Operations¶

    etcd is the key-value store backing the Kubernetes API of each hosted cluster. In HCP, etcd runs as a StatefulSet inside the HCP namespace on the management cluster.

    Architecture¶

    graph LR
    KAS["kube-apiserver\n(HCP namespace)"]
    ETCD["etcd StatefulSet\n(HCP namespace)"]
    PVC["EBS Volume\n(etcd PVC)"]
    S3["S3 Bucket\n(backup)"]

    KAS -->|"reads/writes"| ETCD
    ETCD --> PVC
    ETCD -->|"etcdctl snapshot save"| S3

    style KAS fill:#e3f2fd,color:#0d47a1
    style ETCD fill:#ede7f6,color:#4a148c
    style PVC fill:#e8f5e9,color:#1b5e20
    style S3 fill:#fff3e0,color:#bf360c

    In production, etcd runs as a 3-member cluster (one per AZ) with the etcd-operator managing members.

    Connecting to etcd¶

    SREs never connect to etcd directly. All etcd access is via:

    1. etcdctl commands inside the etcd pod via oc exec
    2. The SSM (AWS Systems Manager) path for worker access

    Prerequisites¶

    export HCP_NAMESPACE="ocm-production-<cluster-id>-<domain-prefix>"
export JIRA_TICKET="<OHSS-XXXXX>"

# Log in to the management cluster
ocm backplane login $CLUSTER_ID --manager

    Getting etcd Health Status¶

    # Run etcdctl endpoint health
ocm backplane elevate "$JIRA_TICKET" -- \
  -n ${HCP_NAMESPACE} exec etcd-0 -c etcd -- \
  sh -c "etcdctl endpoint health \
    --cacert=/etc/etcd/tls/etcd-ca/ca.crt \
    --cert=/etc/etcd/tls/client/etcd-client.crt \
    --key=/etc/etcd/tls/client/etcd-client.key \
    --endpoints=https://localhost:2379"

    Checking etcd Members¶

    ocm backplane elevate "$JIRA_TICKET" -- \
  -n ${HCP_NAMESPACE} exec etcd-0 -c etcd -- \
  sh -c "etcdctl member list \
    --cacert=/etc/etcd/tls/etcd-ca/ca.crt \
    --cert=/etc/etcd/tls/client/etcd-client.crt \
    --key=/etc/etcd/tls/client/etcd-client.key \
    --endpoints=https://localhost:2379 \
    -w table"

    Expected output: 3 members, all started, all true for learner=false.

    Checking etcd Endpoint Status¶

    ocm backplane elevate "$JIRA_TICKET" -- \
  -n ${HCP_NAMESPACE} exec etcd-0 -c etcd -- \
  sh -c "etcdctl endpoint status \
    --cacert=/etc/etcd/tls/etcd-ca/ca.crt \
    --cert=/etc/etcd/tls/client/etcd-client.crt \
    --key=/etc/etcd/tls/client/etcd-client.key \
    --endpoints=https://etcd-0.etcd:2379,https://etcd-1.etcd:2379,https://etcd-2.etcd:2379 \
    -w table"

    Look for: - IS LEADER — the current leader; check that exactly one member is leader - DB SIZE — healthy range depends on cluster usage; alert fires at 3GB/4GB thresholds - RAFT INDEX — all members should be within a few entries of each other

    Checking etcd Alarm Status¶

    ocm backplane elevate "$JIRA_TICKET" -- \
  -n ${HCP_NAMESPACE} exec etcd-0 -c etcd -- \
  sh -c "etcdctl alarm list \
    --cacert=/etc/etcd/tls/etcd-ca/ca.crt \
    --cert=/etc/etcd/tls/client/etcd-client.crt \
    --key=/etc/etcd/tls/client/etcd-client.key \
    --endpoints=https://localhost:2379"

    NOSPACE alarm

    If NOSPACE is in the alarm list, etcd is full and will reject ALL writes. See etcd defragmentation below.

    Defragmentation¶

    etcd accumulates "dark data" (tombstones from deleted keys) over time. Defrag compacts this.

    # Defrag all members (etcd-operator usually handles this automatically)
for pod in etcd-0 etcd-1 etcd-2; do
  ocm backplane elevate "$JIRA_TICKET" -- \
    -n ${HCP_NAMESPACE} exec ${pod} -c etcd -- \
    sh -c "etcdctl defrag \
      --cacert=/etc/etcd/tls/etcd-ca/ca.crt \
      --cert=/etc/etcd/tls/client/etcd-client.crt \
      --key=/etc/etcd/tls/client/etcd-client.key \
      --endpoints=https://localhost:2379"
  echo "Defrag complete on ${pod}"
done

    Defrag is Blocking

    Defrag temporarily suspends reads/writes on the member being defragmented. Always defrag one member at a time. Start with followers before the leader.

    Backup to S3¶

    When to Back Up¶

    • Before any high-risk maintenance (OHSS ticket required)
    • Before etcd member replacement
    • Proactively when DB size is high (>3GB)

    Backup Procedure¶

    # Pause the HostedCluster to stop API writes during snapshot
ocm backplane elevate "$JIRA_TICKET" -- \
  -n ${HC_NAMESPACE} patch hostedcluster ${DOMAIN_PREFIX} \
  --type=merge -p '{"spec":{"pausedUntil":"true"}}'

# Scale down writers to prevent state changes during snapshot
for deploy in kube-apiserver openshift-apiserver oauth-server; do
  ocm backplane elevate "$JIRA_TICKET" -- \
    -n ${HCP_NAMESPACE} scale deployment/${deploy} --replicas=0
done

# Take etcd snapshot
SNAPSHOT_FILE="etcd-snapshot-$(date +%Y%m%d-%H%M%S).db"

ocm backplane elevate "$JIRA_TICKET" -- \
  -n ${HCP_NAMESPACE} exec etcd-0 -c etcd -- \
  sh -c "etcdctl snapshot save /tmp/${SNAPSHOT_FILE} \
    --cacert=/etc/etcd/tls/etcd-ca/ca.crt \
    --cert=/etc/etcd/tls/client/etcd-client.crt \
    --key=/etc/etcd/tls/client/etcd-client.key \
    --endpoints=https://localhost:2379"

# Verify snapshot integrity
ocm backplane elevate "$JIRA_TICKET" -- \
  -n ${HCP_NAMESPACE} exec etcd-0 -c etcd -- \
  sh -c "etcdctl snapshot status /tmp/${SNAPSHOT_FILE} -w table"

# Copy snapshot from pod to local machine
ocm backplane elevate "$JIRA_TICKET" -- \
  -n ${HCP_NAMESPACE} cp etcd-0:/tmp/${SNAPSHOT_FILE} ./${SNAPSHOT_FILE} -c etcd

# Upload to S3 (replace BUCKET_NAME with the cluster's etcd-backup bucket)
BUCKET_NAME="<cluster-etcd-backup-bucket>"
aws s3 cp ./${SNAPSHOT_FILE} s3://${BUCKET_NAME}/manual-backups/${SNAPSHOT_FILE}

# Resume the cluster (scale writers back up, unpause)
for deploy in kube-apiserver openshift-apiserver oauth-server; do
  ocm backplane elevate "$JIRA_TICKET" -- \
    -n ${HCP_NAMESPACE} scale deployment/${deploy} --replicas=1
done

ocm backplane elevate "$JIRA_TICKET" -- \
  -n ${HC_NAMESPACE} patch hostedcluster ${DOMAIN_PREFIX} \
  --type=merge -p '{"spec":{"pausedUntil":"false"}}'

    How Long to Pause?¶

    Metric Impact
    Snapshot time Usually < 60 seconds
    Total API downtime ~3–5 minutes (pause + scale + snapshot + resume)
    Customer workloads NOT affected — only the control plane API pauses

    etcd Operator Tuning¶

    The etcd-operator on HCP handles: - Automatic defragmentation on a schedule - Member replacement when a member fails - PVC expansion when DB size thresholds are hit

    Check etcd-operator logs for automatic actions: 

    osdctl rhobs logs -C $MC_CLUSTER_ID -n ${HCP_NAMESPACE} \
  -c etcd-operator --since 1h
