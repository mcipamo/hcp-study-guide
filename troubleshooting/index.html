    Troubleshooting¶

    Practical troubleshooting procedures for ROSA HCP clusters — from gathering evidence to diagnosing specific failure modes.

    Must-Gather Collection¶

    The osdctl hcp must-gather command is the primary tool for collecting diagnostic data from an HCP cluster.

    Basic Usage¶

    export CLUSTER_ID="<cluster-id>"
export JIRA_TICKET="<OHSS-XXXXX>"

# Collect must-gather for the HCP cluster (default: hcp target)
osdctl hcp must-gather --cluster-id $CLUSTER_ID --reason $JIRA_TICKET

# Collect from the service cluster (ManifestWorks, ACM state)
osdctl hcp must-gather --cluster-id $CLUSTER_ID --target sc --reason $JIRA_TICKET

# Collect from the management cluster's ACM hub
osdctl hcp must-gather --cluster-id $CLUSTER_ID --target sc_acm --reason $JIRA_TICKET

# Collect from the management cluster directly
osdctl hcp must-gather --cluster-id $CLUSTER_ID --target mc --reason $JIRA_TICKET

    What Each Target Collects¶

    Target Collects
    hcp (default) Control plane pod logs, HCP CRs, conditions
    sc ManifestWorks, SC-level operator state
    sc_acm ACM hub state (ManagedClusters, ACM operator)
    mc MC cluster-level resources (not HCP namespace)

    Analyzing with omc¶

    # After collecting must-gather:
ls must-gather.local.*

# Use omc to analyze (like 'oc' but reads from must-gather directory)
omc use ./must-gather.local.TIMESTAMP/
omc get pods -n $HCP_NAMESPACE
omc logs -n $HCP_NAMESPACE <pod-name>

    Noisy Neighbor Mitigation¶

    A "noisy neighbor" occurs when one or more HCPs on an MC consume so much CPU/memory that other HCPs degrade.

    Diagnosis¶

    # Find the top CPU-consuming HCP namespaces on an MC
ocm backplane login $HCP_CLUSTER_ID --manager
oc adm top pods -A --sort-by=cpu | head -20

# Check which HCPs are on the noisy MC
ocm get /api/osd_fleet_mgmt/v1/management_clusters | \
  jq -r '.items[] | select(.cluster_management_reference.cluster_id == "'$MC_ID'") | .managed_clusters[]?.id'

# Look for resource-intensive operations (large etcd DB, high API rate)
oc get hostedclusters -A -o json | \
  jq -r '.items[] | [.metadata.name, .status.etcd.dbSize, .status.conditions[]?.reason] | @tsv'

    Mitigation 1: Request Non-Serving Node Resize¶

    The standard fix for node-level pressure is to resize the non-serving (worker) nodes of the overwhelmed MC pair. See Node Operations.

    Mitigation 2: Isolate to a Dedicated MachinePool¶

    Isolate the noisy HCP to a dedicated set of nodes using MachinePool labels/taints:

    # Label the dedicated machinepool nodes
oc label node $NODE_NAME dedicated=tenant-A

# Add taint to prevent other HCPs from scheduling
oc taint node $NODE_NAME dedicated=tenant-A:NoSchedule

# Patch the HostedControlPlane to use the dedicated nodes
ocm backplane elevate "$JIRA_TICKET" -- \
  -n $HCP_NAMESPACE patch hostedcontrolplane $DOMAIN_PREFIX \
  --type=merge -p '{
    "spec": {
      "nodeSelector": {"dedicated": "tenant-A"},
      "tolerations": [{"key": "dedicated", "value": "tenant-A", "effect": "NoSchedule"}]
    }
  }'

    MC Worker EBS Snapshot¶

    Before replacing a worker node or troubleshooting disk corruption, capture an EBS snapshot:

    # Find the instance ID of the MC worker node
INSTANCE_ID=$(oc get node $NODE_NAME -o json | \
  jq -r '.spec.providerID | split("/") | last')

# Find the root EBS volume
ROOT_VOL=$(aws ec2 describe-instances \
  --instance-ids $INSTANCE_ID \
  --query 'Reservations[].Instances[].BlockDeviceMappings[?DeviceName==`/dev/xvda`].Ebs.VolumeId' \
  --output text)

# Take snapshot
SNAPSHOT_ID=$(aws ec2 create-snapshot \
  --volume-id $ROOT_VOL \
  --description "pre-investigation snapshot of $NODE_NAME ($JIRA_TICKET)" \
  --tag-specifications "ResourceType=snapshot,Tags=[{Key=cluster,Value=$MC_CLUSTER_ID},{Key=node,Value=$NODE_NAME},{Key=ticket,Value=$JIRA_TICKET}]" \
  --query 'SnapshotId' --output text)

echo "Snapshot: $SNAPSHOT_ID"

# Wait for completion
aws ec2 wait snapshot-completed --snapshot-ids $SNAPSHOT_ID
echo "Snapshot complete"

    Port Forward Without Debug Handler¶

    MC worker nodes don't have the backplane debug handler. Use a proxy pod to forward ports to pods in the HCP namespace:

    # Create a proxy pod that can forward to the etcd service
cat <<EOF | ocm backplane elevate "$JIRA_TICKET" -- apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: proxy-pod
  namespace: $HCP_NAMESPACE
spec:
  containers:
  - name: proxy
    image: registry.access.redhat.com/ubi9/ubi-minimal:latest
    command: ["sleep", "3600"]
    ports:
    - containerPort: 2379
EOF

# Wait for the pod to start
oc wait pod/proxy-pod -n $HCP_NAMESPACE --for=condition=Ready --timeout=60s

# Port-forward through the proxy pod
ocm backplane elevate "$JIRA_TICKET" -- \
  port-forward -n $HCP_NAMESPACE pod/proxy-pod 2379:2379 &

# Now local:2379 maps to the pod's port 2379
# You can redirect this to the etcd service from inside the pod:
ocm backplane elevate "$JIRA_TICKET" -- \
  -n $HCP_NAMESPACE exec proxy-pod -- \
  sh -c "nc -l -p 2379 -e nc etcd-client 2379"

# Clean up when done
oc delete pod proxy-pod -n $HCP_NAMESPACE

    Worker Node Access¶

    Method 1: SSH via Jumphost Bastion¶

    For public HCP clusters (API endpoint is public):

    # Find the customer's SSH key secret
oc get hostedcluster $CLUSTER_NAME -n $HC_NS \
  -o jsonpath='{.spec.sshKey.name}'

# Get the worker node's private IP
oc get node $NODE_NAME -o jsonpath='{.status.addresses[?(@.type=="InternalIP")].address}'

# In ROSA HCP, SSH access to worker nodes requires:
# 1. The customer's SSH key pair (specified at cluster creation)
# 2. Access to the customer's VPC (via PrivateLink or public bastions)
# Worker nodes do NOT have public IPs by default

    Method 2: Jumphost to Workers (osdctl)¶

    # For private clusters, use osdctl's backplane-based jumphost
osdctl hcp worker-shell $CLUSTER_ID $NODE_NAME

# This establishes an SSH connection via:
# SRE laptop → backplane proxy → MC → PrivateLink → customer VPC → worker node

    Method 3: Privileged Debug Pod on MC¶

    Run a privileged pod on the same MC node for host-level debugging:

    # This requires the specific MC node that runs the worker
ocm backplane login $CLUSTER_ID --manager

# Find which MC node is hosting the troubled worker's HCP pod
oc get pods -n $HCP_NAMESPACE -o wide | grep kube-apiserver

# Run a privileged debug pod on that MC node
ocm backplane elevate "$JIRA_TICKET" -- debug node/$MC_NODE_NAME

    Route53 Quota Issues¶

    If clusters fail to create with Route53QuotaExceeded or DNS delegation failures:

    # Check hosted zones in use
aws route53 list-hosted-zones | jq '.HostedZones | length'
# Default limit: 500 hosted zones per account

# Check records per zone
aws route53 list-resource-record-sets \
  --hosted-zone-id $ZONE_ID | jq '.ResourceRecordSets | length'
# Default limit: 10,000 records per zone

# Request quota increase (file SR with AWS Support)
aws service-quotas create-case \
  --service-code route53 \
  --quota-code L-4EA4796A \
  --desired-value 1000

    Transit Gateway + Route53 VPC Association¶

    For PrivateLink and private DNS resolution across multiple VPCs/accounts:

    # Associate a Route53 hosted zone with a VPC in another account
# (requires cross-account authorization)

# Step 1: Authorize the association (in the hosted zone's account)
aws route53 create-vpc-association-authorization \
  --hosted-zone-id $ZONE_ID \
  --vpc VPCRegion=us-east-1,VPCId=$CUSTOMER_VPC_ID

# Step 2: Associate (in the VPC's account)
aws route53 associate-vpc-with-hosted-zone \
  --hosted-zone-id $ZONE_ID \
  --vpc VPCRegion=us-east-1,VPCId=$CUSTOMER_VPC_ID

# Step 3: Delete the authorization (cleanup)
aws route53 delete-vpc-association-authorization \
  --hosted-zone-id $ZONE_ID \
  --vpc VPCRegion=us-east-1,VPCId=$CUSTOMER_VPC_ID

# Verify association
aws route53 get-hosted-zone --id $ZONE_ID | \
  jq '.VPCs[] | select(.VPCId == "'$CUSTOMER_VPC_ID'")'
